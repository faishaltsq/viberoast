# Authenticated Hall Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans task-by-task. Track steps with checkboxes.

**Goal:** Deliver OAuth-protected, bilingual, fictional educational case files without changing anonymous scanning.

**Architecture:** Supabase SSR validates sessions on the server for `/hall` and `/api/hall`; a narrowly matched proxy refreshes cookies. Separate strict Hall schemas and curated bilingual fixtures feed existing-style gallery and native modal UI. No report-store dependency or publication feature.

**Tech Stack:** Next 16.4.3, React 19, TypeScript, Zod 4, Supabase SSR/Auth, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-03-hall-auth-design.md`

## Global Constraints

- Worktree `hall-auth`, branch `feat/hall-auth-anonymous-case-files`, base `666ec9f`.
- Website Judge and Repository Judge remain available without authentication.
- No security/scanner/provider/report contract edits; no real publication or database publication schema.
- SourceSanity/Bro Code, EN/ID, original visual identity and mascot.
- Mock external auth transport, never add an authentication bypass to production.
- No merge/deploy; no credentials committed. Live OAuth explicitly pending configuration.

## Review Focus

1. Expired or forged sessions must fail both server page and API guards.
2. Callback targets with encoded separators, external hosts or unapproved paths must never redirect off-site.
3. Cookie refresh and failed logout cannot leave a misleading authenticated UI.
4. Modal language changes must not reset filters, scroll or trigger restoration.
5. Hall payloads cannot accept arbitrary raw reports, identifying fields or secrets.
